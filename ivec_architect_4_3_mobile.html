アーキテクトクラス｜4.3 テスト評価
Chapter 4.3 — 汎用テスト知識・スキル
テスト評価
テスト報告書を含むテスト活動の全情報・結果を用いてテスト活動の達成度合いを分析・評価する。ポストモーテムを行いプロジェクト成果および改善点を展開する。
4.3.1
テスト報告書を準備する

テスト報告フェーズで作成したテスト報告書を準備する。テスト報告書に加え、レビュー結果などの付帯情報も合わせて用意する。入手した情報は時系列やイベントごとに整理して分析しやすくする。

INPUT
  • テスト報告に関する入手物一覧表またはチェックシート
OUTPUT
  • テスト報告書一式
  • スケジュール（工程）の予定／実績
  • 工数の予定／実績データ
  • 各アウトプットのレビュー結果
  • 参考にできる他プロジェクトの情報
  • 前回プロジェクトの情報
実施タスク
① 該当のテスト報告書を入手する。入手時にはテストの計画と実績・変更履歴・レビュー結果など、チェックシートに基づき必要な情報の有無を確認する
② 入手した情報はテスト活動の時系列やイベントごとに整理する
③ 参考になる過去の類似プロジェクトのデータ・前回からの引継ぎ事項（前回の改善事項）も用意する
4.3.2
テスト活動全般の情報を収集する

テスト活動に関するプロジェクトの情報を広く収集する。テスト報告書だけでなく、計画・実績（エビデンス）・変更要求なども収集対象となる。

INPUT
  • テスト報告に関する入手物一覧表またはチェックシート
OUTPUT（活動情報事例）
  • マスターテスト計画書
  • プロジェクト計画書
  • テスト要求分析書（スコープ）
  • レベルテスト計画書
  • 各レビュー結果
収集するプロジェクト情報の事例
テストスコープ、テストタスク、コスト計画と実績、品質計画と実績、組織計画と実績（要員の調達・確保・トレーニング計画と実績）、コミュニケーション計画、リスク管理計画と実績（リスク定義書・対策計画書）、調達計画と実績、プロジェクト改善計画（目標）
実施タスク
① 該当のテスト活動の情報をチェックシートに基づいて入手する
② 入手した情報はテスト活動の時系列やイベントごとに整理する
4.3.3
テスト活動を分析する

テスト活動の分析には2種類ある。

①テスト活動の評価分析：テスト計画と実績の対比、プロジェクトへの変更要求とその対応、テスト活動中に発生したトラブルとリカバリなどの分析

②技術資産の蓄積のための分析：テストアーキテクチャ設計・テスト詳細設計・テスト実装・テスト実行・テスト報告の成果物に対して実績データなどを分析

INPUT
  • テスト活動への改善施策（プロジェクト改善計画書等）
  • テスト報告書一式
  • テスト活動情報一式
OUTPUT
  • テスト設計情報
  • テスト実績データ
  • 比較データ
  • プロセス成熟度判定結果
実施タスク
① テスト活動を時系列に整理し、テスト活動に関する経験（暗黙知・ノウハウ）を定量的および定性的な情報として記録する。テストリポジトリを構築している場合はデータを登録する
② テスト活動の定量的データ（実績データ）と基準となる指標のデータを比較して、テスト活動におけるボトルネックを抽出する
③ 標準テストプロセスとの比較やTMapなどを利用してプロセスの成熟度を計測する
🎯 学習のポイント
ボトルネックを抽出することで、テスト計画と実績の差異を指標を用いて数値的なデータから分析できる。例：テスト設計した項目数の予実を確認し、大幅な差異がある場合はなぜ差異が出たかを分析し、見積精度の改善につなげる。
📘 TMap とは
TMap（Test Management approach for structured testing）は、20のキーエリアを13のスケールで構造化したテストプロセスの方法論。SOGETI社によって提案され、テストプロセス改善に用いられる。
4.3.4
前回の改善項目の達成率を評価する

テスト活動に対する改善計画に基づいて、改善項目の達成度について数値的な分析を行う。担当者の感想だけでなく実績データとの比較による客観的な評価が重要。

INPUT
  • プロジェクト改善計画書
  • 改善のねらい（効果）
  • 改善項目（目標）
  • 改善のタスク
OUTPUT
  • 改善目標の達成率
  • 改善のねらいの達成度合い
  • 改善のタスクの実施程度
  • 改善未達成項目
  • 新たな改善項目
実施タスク
① プロジェクト改善計画で立案した改善項目とテスト活動の実績データを比較し、達成率を算出する
② 改善のねらい（効果）に対して改善タスクの実施程度を考慮して、定性的な目的の達成度合いを判定する
③ 改善が不十分な項目や新たな改善すべき項目を抽出する
🎯 学習のポイント
テスト評価作業では、次回のプロジェクトを効率的に行えるよう評価する。担当者からの意見・感想（アンケート等）だけでなく、数値的に実績データと比較することで客観的に評価する。
4.3.5
分析結果と評価指標を比較する

改善の達成率・達成度合いからプロジェクト改善の目的との差異を比較し、満足度（充足度）を判定する。評価指標の見直しも行う。

INPUT
  • 改善目標の達成率
  • 改善のねらいの達成度合い
OUTPUT
  • プロジェクト改善の全体達成率
  • 評価指標の見直し項目
実施タスク
プロジェクト改善の目的との差異を、改善目標の達成率や改善のねらいの達成度合いで満足度（充足度）を判定する。プロジェクトの改善の満足度から、評価指標の見直しを行う。
4.3.6
改善点（良かった点・悪かった点）を抽出する

プロジェクト関係者から成果および反省点を広く収集する。役割の異なる関係者でのギャップ分析も行う。

INPUT
  • プロジェクト成果および反省点のアンケート
OUTPUT
  • 改善点（良かった点・悪かった点）
  • プロジェクト成果一覧／詳細
  • プロジェクト反省点一覧／詳細
実施タスク
① プロジェクトの関係者から広く成果および反省点を収集する
② 役割の異なる関係者で、プロジェクトに対する成果・反省点のギャップを分析する
③ 分析した結果を一覧化して詳細を記録する
4.3.7
改善策を検討する

プロジェクトの改善点の影響度・効果などを分析し、優先度や対策を検討して次期プロジェクトへ展開する。

INPUT
  • 改善点（良かった点・悪かった点）
  • プロジェクト成果一覧／詳細
  • プロジェクト反省点一覧／詳細
OUTPUT
  • 改善処置対策書
実施タスク
プロジェクトの反省点・改善点の影響度合いを分析する。影響度合いが高く、発生する確率／回数が多い項目の優先度を高く設定し、根治対策または回避方策を検討する。また改善点に対して再発防止策を検討する。
4.3.8
テスト評価報告書を作成する

テスト活動の分析結果・評価結果・改善点などを広く水平展開できるよう体系的に整理して、テスト評価報告書を作成する。

INPUT
  • テスト評価の分析・改善評価結果
  • テスト報告書
  • テスト活動の分析結果
  • 改善計画と達成率・改善分析結果
OUTPUT
  • テスト評価報告書
  • テスト活動改善計画
  • テスト活動計画対比分析
  • 達成指標（達成項目／未達成項目）
  • 次期改善点一覧
  • 技術蓄積情報一覧（保管情報）
実施タスク
該当するテスト活動の改善施策の視点で、テスト活動の分析結果や評価結果を整理する。各評価結果は関連性が明確になるような書式で文書化する。
4.3.9
テスト評価報告書を開示する

テスト評価報告会などを通じてテスト評価報告書を関係者に開示する。テスト活動の技術情報・改善成果・失敗事例などは他のテスト活動のプロジェクトにも広く水平展開する。

INPUT
  • テスト評価報告書
OUTPUT
  • 開示先一覧
  • テスト評価報告書へのコメント／指摘事項
  • 報告会の議事録
  • 次回プロジェクトへの引継ぎ資料
実施タスク
テスト評価報告会を実施して広くテスト評価報告書を開示する。報告会を通じてテスト評価に関するコメントや指摘事項を収集し、次回プロジェクトへの引継ぎ資料として報告会の内容（指摘された点など）を議事録にまとめる。

■ 記述問題
Q14記述4.3.3
テスト活動を分析する2種類の分析を、それぞれの目的と分析対象を含めて説明せよ。
📝 解答例
①テスト活動の評価分析：テスト計画と実績の対比、プロジェクトへの変更要求とその対応、テスト活動中に発生したトラブルとリカバリなど、テスト活動の結果に対して分析を行う。②技術資産の蓄積のための分析：テストアーキテクチャ設計・テスト詳細設計・テスト実装・テスト実行・テスト報告などの成果物に対して、実績データなどの分析を行う。
Q15記述4.3.4
前回の改善項目の達成率評価において、定量的評価と定性的評価をそれぞれどのように行うか説明せよ。
📝 解答例
定量的評価：プロジェクト改善計画で立案した改善項目とテスト活動の実績データを比較し、達成率を算出する。定性的評価：改善のねらい（効果）に対して改善のタスクの実施程度などを考慮して、目的の達成度合いを判定する。どちらも担当者の意見・感想だけでなく客観的な評価を重視する。
Q16記述4.3.6
改善点の抽出において「役割の異なる関係者でギャップを分析する」ことの意義を説明せよ。
📝 解答例
役割が異なる関係者（例：テスト担当者・開発者・マネージャーなど）では、同じプロジェクトに対して成果や反省点の認識が異なる場合がある。そのギャップを分析することで、一つの視点では見えなかった課題や改善点を広く収集・把握でき、より網羅的な改善につなげることができる。
Q17記述4.3.3
テスト活動の分析においてTMapを利用する目的を説明し、TMapの特徴を簡潔に述べよ。
📝 解答例
目的：標準テストプロセスとの比較を行いプロセスの成熟度を計測するために利用する。特徴：TMapはSOGETI社によって提案されたテストプロセスの方法論で、20のキーエリアを13のスケールで構造化している。テストプロセス改善に活用される。
Q18記述4.3.8
テスト評価報告書を「水平展開」するとはどういうことか、テスト評価報告書開示（4.3.9）の内容を踏まえて説明せよ。
📝 解答例
水平展開とは、テスト活動の技術情報・改善成果・失敗事例などを自プロジェクト内にとどめず、他のテスト活動のプロジェクトにも広く共有・活用することを指す。4.3.9ではテスト評価報告会を実施して広く開示し、報告会でのコメントや指摘事項を収集し次回プロジェクトへの引継ぎ資料として議事録にまとめることで、組織全体のテスト技術の向上につなげる。

Q「改善が不十分な項目や新たな改善すべき項目を抽出する」のはどの節の実施タスクか？
4.3.4「前回の改善項目の達成率を評価する」の実施タスク。
Q4.3.5で判定する「満足度（充足度）」とは何を基に判定するか？
改善目標の達成率と改善のねらいの達成度合いを基に、プロジェクト改善の目的との差異を比較して判定する。
Q4.3.5のINPUT2つとOUTPUT2つは？
INPUT：①改善目標の達成率　②改善のねらいの達成度合い。OUTPUT：①プロジェクト改善の全体達成率　②評価指標の見直し項目
Q4.3.6「改善点の抽出」のINPUTとOUTPUTは？
INPUT：プロジェクト成果および反省点のアンケート。OUTPUT：①改善点（良かった点・悪かった点）　②プロジェクト成果一覧/詳細　③プロジェクト反省点一覧/詳細
Q改善策検討における「根治対策」と「回避方策」の違いは？
根治対策は問題の根本原因を取り除く対策。回避方策は問題が発生した場合の回避手段を講じる方策。どちらも影響度合いが高く発生頻度が多い項目に対して優先的に検討する。
Q4.3.7のOUTPUT（成果物）は何か？
改善処置対策書
Q4.3.8のOUTPUTを全て挙げよ。
①テスト評価報告書　②テスト活動改善計画　③テスト活動計画対比分析　④達成指標（達成項目／未達成項目）　⑤次期改善点一覧　⑥技術蓄積情報一覧（保管情報）
Qテスト評価報告書の文書化において「改善施策の視点で整理する」とはどういうことか？
該当するテスト活動の改善施策（次回どう改善するか）の観点から、テスト活動の分析結果や評価結果を整理すること。関連性が明確になるような書式で文書化することが求められる。
Q4.3.9のOUTPUT4つは？
①開示先一覧　②テスト評価報告書へのコメント／指摘事項　③報告会（実施した場合）の議事録　④次回プロジェクトへの引継ぎ資料
Qテスト活動の「水平展開」とは何をすることか？
テスト活動の技術情報・改善成果・失敗事例などを、自プロジェクトにとどめず他のテスト活動のプロジェクトにも広く共有・活用することを指す。
Q4.3.2で収集するプロジェクト情報のうち「リスク管理」に関する収集物は？
リスク管理計画と実績（リスク定義書・対策計画書）。顕在化したリスクの対応率なども含む。
Qテスト活動の分析でプロセス成熟度を計測する方法として挙げられている2つは？
①標準テストプロセスとの比較　②TMapなどの活用
Qプロジェクト改善計画書はいつ作成されるか？
テストプロジェクトの立ち上げ時に前回の改善課題がある場合に作成される。すべてのテスト工程（テスト詳細設計・テスト実行などの工程）で立案・作成される。
Q4.3.6「改善点の抽出」で収集する対象は誰か？
プロジェクト関係者（広く収集する）。役割の異なる関係者でプロジェクトに対する成果・反省点のギャップを分析することが重要。
