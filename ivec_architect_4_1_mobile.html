4.1 テスト要求分析
🏠 TOP
Chapter 4.1 — 汎用テスト知識・スキル
テスト要求分析
テスト対象・対象外の範囲や制約事項を収集・分析し、テスト要件として定義するプロセス。テスト活動のゴール（終了基準・リリース基準）の根拠となる。
4.1.1
テスト要求分析の準備をする

テスト要求分析の準備フェーズでは、インタビューやドキュメントから要求を引き出すための土台を整える。ステークホルダを特定してアサインし、入手すべき情報の種類と取得経路の正当性を明確にすることが求められる。

開発中や要件未決定などで情報が得られない場合は、不足情報を一覧化してタスク管理し、受身にならず期限を設けて入手を促す。

INPUT
  • マスターテスト計画
  • テスト要求の取得概要（一覧）
  • ドキュメントベースのテスト要求
  • 要求仕様書・開発設計書
  • 過去テスト計画書・報告書
OUTPUT
  • テスト要求の取得概要（一覧）
  • インタビュー報告書
  • 議事録等
  • 不足情報の管理表
実施タスク①
テスト要求に必要な入力を整理する。マスターテスト計画から該当するテストレベルを確認し、取得すべき情報を整理する。
🎯 学習のポイント
取得すべき情報を整理する目的は「何をもってテスト要求を決定したか、データの出所を明らかにすること」。要求を可視化することで、テストの終了判定時の証跡となる。
実施タスク②
適切なドキュメントを入手し、一覧を作成してバージョンと入手元を記録する。
🎯 学習のポイント
ドキュメント一覧を記録することで、作成したテスト要求の根拠をトレースできる仕組みを確立できる。
実施タスク③
不足情報が得られない場合は一覧化し、入手の可否・時期・担当者を設定してタスク管理する。
🎯 学習のポイント
「いつまでに」不足情報を入手するかを設定し、受身にならずステークホルダへ積極的に要求することが重要。
4.1.2
テスト要求を獲得する

準備で収集したドキュメントやインタビュー情報から、テスト要求にインプットする情報を抽出する。入手した情報が「要求」なのか「阻害要因」なのかを分類・関連付けする。

一方的に情報を収集するのではなく、収集した情報を整備して妥当な情報であることを要求元と確認することが重要。

INPUT
  • 品質計画
  • マネジメントシステム（品質/環境/セキュリティ等）
  • マスターテスト計画書
  • 開発仕様書・プロジェクト計画書
  • テスト対象の利用環境に関する情報
OUTPUT
  • 品質方針・テスト目的・品質目標
  • テストベース一覧
  • テスト対象/対象外範囲の一覧
  • 概算コスト・大まかなスケジュール
実施タスク（主要5項目）
1. 企業の品質方針/コンセプトを確認し品質評価手法を検討
2. マスターテスト計画書からテストレベルの範囲とテスト目的を獲得
3. 要求仕様書から品質要求を想定し品質目標を定義
4. テストベース情報を入手して一覧化
5. テスト環境情報・コンプライアンス情報を収集
🎯 学習のポイント
コンプライアンス要件（法令・規格）は仕様書に暗黙知として明示されない場合がある。規格違反を見逃さないために事前の情報収集が不可欠。
4.1.3
テスト要求を分析する

獲得したテスト要求情報を分析し、必要な関連付けを行って体系的に整理する。テスト目的（スコープ）を定義し、制約事項の有無を整理する。

INPUT
  • 品質方針・品質特性
  • テスト対象のコンセプト
  • 品質要求・品質目標
  • テストベース一覧
  • 要件定義書・マスターテスト計画書
  • コンプライアンス情報・テスト環境要求
OUTPUT
  • テスト目的の詳細・構造（可視化）
  • テスト目標の詳細・構造（可視化）
  • 整合性確認済テストベース一覧
  • テスト範囲の分析結果レポート
  • テスト対象の問題・課題一覧
  • テスト環境要求一覧
実施タスク（主要項目）
1. 品質方針確認 → 品質特性分析（ISO/IEC 25010活用） → テスト目的の詳細化・構造化
2. 品質要求/品質目標からテスト目標の詳細化
3. テストベース一覧と要件定義書・品質特性との整合性確認
4. テストレベルの対象範囲から範囲の深さを策定
5. 開発進捗状況レポートとの差異を抽出しテスト計画へのリスクを分析
🎯 学習のポイント
「範囲の深さ」とは例えば、性能要求に対してモジュール単位で見るか、システム全体で見るかをテストレベルで決めること。品質目標の定義過程は後工程で参照するために記録・構造化を推奨。
4.1.4
テスト要求分析成果物を作成する

テスト要求分析結果を整理して成果物を作成する。インプット項目と分析結果を可視化・関連付けすることで、テスト要求のカバレッジとトレーサビリティを確保する。

INPUT
  • テスト要求の分析結果
OUTPUT
  • テスト要求分析成果物（下記6項目を網羅）
成果物に含めるべき6項目
1. テスト目的
2. 品質目標
3. テストベース
4. テスト対象範囲
5. テスト対象外範囲
6. テスト対象の開発状況・テスト環境（テストベンチ）
🎯 学習のポイント
記載が曖昧になりがちな「テスト対象外範囲」を明確にすることが特に重要。「なぜ対象外か」「誰の責務で実施すべきか」を明確にすることで、早期に役割分担を調整できる。
4.1.5
テスト要求分析成果物を検証する

テスト要求分析成果物に対して要求元と公式レビューを行い、内容の過不足や整合性を確認する。

INPUT
  • テスト要求分析成果物
OUTPUT
  • レビュー記録
  • レビューフォローアップ
  • 承認されたテスト要求分析成果物
実施タスク
1. 要求元および関係者と公式レビューを行い、要求の漏れと整合性を確認
2. 指摘事項があればレビュー記録に基づいてフォローアップ
3. 全フォローアップ完了後、要求元の承認を得る
🎯 学習のポイント
レビュー基準・レビュー規約が整備されている場合はそれに準じる。整備されていない場合はどのようにレビューを行うかを必ず確認する。

■ 四択問題
Q01四択4.1.1
テスト要求分析の準備フェーズにおいて、入手すべきドキュメントの一覧を作成し各々のバージョンと入手元を記録することの主な目的は何か。
✅ 正解：B
入手したドキュメントの一覧を作成・記録することで、整理したテスト要求が何に基づくものかトレースできる仕組みが構築される。これにより、作成したテスト要求の根拠を主張できる。
Q02四択4.1.1
開発中や要件未決定などでヒアリング結果が得られない場合、アーキテクトはどのように対処すべきか。
✅ 正解：C
一覧化したタスクに「いつまでに」不足情報を入手するかを設定し、受身にならず管理してステークホルダに要求することが重要。
Q03四択4.1.2
テスト要求の獲得において、コンプライアンス情報を事前に収集する理由として最も適切なものはどれか。
✅ 正解：D
テスト対象が利用される環境における法令や規格は、暗黙知として仕様書に明示されないことがある。規格違反を見逃さないために事前にコンプライアンス情報を収集する。
Q04四択4.1.3
テスト要求分析において品質特性を分析する際に活用が推奨される国際規格はどれか。
✅ 正解：B
ISO/IEC 25010は品質特性を定義した規格で、テスト観点として活用できる。テスト対象が利用される環境と担当するテストレベルを考慮して分析すると効率的。
Q05四択4.1.4
テスト要求分析成果物において特に記載が曖昧になりがちで、明確化が重要な項目はどれか。
✅ 正解：C
テスト対象外範囲は記載が曖昧になりがち。「なぜ対象外か」「誰の責務で実施すべきか」を明確にすることで、検討漏れがあった場合に早期に役割分担を調整できる。
Q06四択4.1.5
テスト要求分析成果物の公式レビューにおいて、全てのフォローアップが完了した後に行うべきことは何か。
✅ 正解：B
全てのレビューフォローアップが完了したら、要求元の承認を得る。これが公式レビューの完了条件。

■ 記述問題
Q11記述4.1.1
テスト要求分析の準備フェーズにおいて、ステークホルダへのインタビューをアサインする前に行うべきことと、その理由を説明せよ。
📝 解答例
インタビュー前に「誰から、何をヒアリングしたいのか」を事前に整理しておく。理由：繰り返し同じステークホルダへヒアリングしないようにするためであり、最初にステークホルダを明らかにして事前準備することで効率よくヒアリングを実施できるから。
Q12記述4.1.2
テスト要求獲得において、テストベースを一覧化することの目的を説明せよ。
📝 解答例
テストベースを一覧化することで入手する情報が可視化され、入手すべき情報の漏れ防止につながる。
Q13記述4.1.3
「範囲の深さ」という概念について、性能要求を例に挙げて説明せよ。
📝 解答例
範囲の深さとは、テスト対象の確認粒度を指す。例えば性能要求に対してモジュール単位の応答時間を確認するのか、システム全体の応答時間を確認するのかは、テストレベルの対象範囲によって決まる。また性能測定時のメモリ使用量やCPU使用率をどこまで意識するかも検討が必要。
Q14記述4.1.4
テスト要求分析成果物において「テスト対象外範囲」を明確にする意義を述べよ。
📝 解答例
テスト対象外範囲を明確にすることで、検討漏れがあった場合に早い段階で役割分担を調整できる。「なぜ対象外にしたのか」「対象外にした範囲は誰の責務で実施すべきか（もしくは実施しないのか）」を明確化することで、後工程での手戻りを防ぐ。
Q15記述4.1.5
テスト要求分析成果物のレビューにおいて、組織にレビュー基準やレビュー規約が整備されていない場合はどのように対応すべきか。
📝 解答例
レビュー基準・レビュー規約などの手続きが整備されていない場合は、どのようにレビューを行うかを関係者と必ず確認する。整備されている場合はそれに準じてレビューを実施する。

Qテスト要求分析の準備フェーズで入手すべき情報を整理する目的は何か？
何をもってテスト要求を決定したか、データの出所を明らかにすること。要求を可視化することでテストの終了判定時の証跡となる。
Q準備フェーズで不足情報が得られない場合の対処方法は？
不足情報を一覧化し、今後の入手の可否・時期・担当者を設定してタスク管理する。受身にならずステークホルダに要求することが重要。
Qインタビュー前に「誰から何をヒアリングしたいか」を整理する理由は？
繰り返し同じステークホルダへヒアリングしないようにするため。事前整理で効率よくヒアリングを実施できる。
Qテスト要求の獲得において、入手した情報はどの2つに分類するか？
「要求」と「阻害要因」に分類する。さらに様々な関連付けを実施する。
Qテストベースを一覧化することの目的は？
入手する情報が可視化され、入手すべき情報の漏れ防止につながる。
Qテスト対象のコンセプトとは何か？
テスト対象が提供する価値のこと。コンセプトを把握することで、テスト対象に必要なテストや目標とする品質を検討できる。
Qテスト要求獲得時にコンプライアンス情報を収集する理由は？
法令や規格は暗黙知として仕様書に明示されない場合がある。規格違反を見逃さないために事前収集が必要。
Q品質特性の分析で活用が推奨される国際規格は？
ISO/IEC 25010（品質特性を定義した規格）。テスト対象が利用される環境と担当するテストレベルを考慮して分析する。
Q「範囲の深さ」とは何を意味するか？
例えば性能要求に対してモジュール単位の応答時間を確認するのか、システム全体の応答時間を確認するのかという、テスト確認の粒度のこと。
Q品質方針が適用されるISO規格は何か、そのシステムの略称も含めて答えよ。
ISO 9000（品質マネジメントシステム、QMS）。QMSを適用している組織では品質についての方針やマニュアルが整備されている。
Q開発進捗状況レポートとマスターテスト計画書を比較する目的は？
テスト計画に影響がある箇所を分析するため。開発の進捗・実装状況からテストの順序や単位時間あたりの消化件数への影響を把握し、リスクを事前に特定する。
Qテスト要求分析成果物に含めるべき6つの項目は？
①テスト目的　②品質目標　③テストベース　④テスト対象範囲　⑤テスト対象外範囲　⑥テスト対象の開発状況・テスト環境（テストベンチ）
Qテスト要求分析成果物においてカバレッジとトレーサビリティを確保する方法は？
テスト要求へのインプット項目とテスト要求分析結果を可視化し関係付けを行うことで確保する。
Q「テスト対象外範囲」を成果物に明記する意義は？
なぜ対象外にしたのか、誰の責務で実施されるべきかを明確にすることで、検討漏れがあった場合に早い段階で役割分担を調整できる。
Qテスト要求分析成果物のレビューで確認すべき2点は？
①要求に漏れがないこと　②要求との整合性が確認されていること
Qレビューのフォローアップとは何を指すか？
レビューで指摘事項があった場合に、レビュー記録に基づいて指摘内容を修正・対応すること。全フォローアップ完了後に要求元の承認を得る。
Qレビュー基準・規約がない場合の対応は？
どのようにレビューを行うかを関係者と必ず確認する。
Qテスト要求分析の主要インプットのうち「過去」の資料に該当するものは？
過去テスト計画書・報告書（4.1.1のINPUT）
Qテスト環境情報を収集する際に念頭に置くべき内容は？
テスト対象を動作させる環境だけでなく、ロギングツールやシミュレータなど必要なツール類も含めて情報を入手する。テスト環境の準備は後のテスト実行やコストに大きな影響を与える。
Qテスト要求分析において品質目標の定義過程を記録・構造化する理由は？
後工程の計画立案時などで参照するため。構造化することで参照を容易にする。また、テスト終了判定などにも用いられる。
