アーキテクトクラス｜4.2 テストアーキテクチャ設計
Chapter 4.2 — 汎用テスト知識・スキル
テストアーキテクチャ設計
テスト要求分析の結果からテストの実現方式を立案する。品質特性・環境を考慮したテストツール・技法・マネジメント方法・テストベンチを選定・定義する。
4.2.1
テスト要求分析成果物を準備する

テストアーキテクチャ設計を開始するために、テスト要求分析の成果物一覧を確認し、必要な成果物を揃える。テスト活動への要求の漏れを防止することが目的。

INPUT
  • テスト要求分析の成果物一覧
OUTPUT
  • テスト要求分析成果物入手済一覧表
実施タスク
一覧を基に実物を確認する。不足している場合は入手時期を明らかにする。
4.2.2
テストベースを準備する

テスト対象の開発成果物などテストベースを準備する。入手したテストベースは入手元・履歴・管理方法を定義して管理する。開発の状況によって改変される可能性があることを考慮しておく。

INPUT
  • テストベース一覧
OUTPUT
  • テストベース
  • テストベースの管理（履歴/場所/方法/管理者）
実施タスク
必要なテストベースを入手し、履歴／管理場所／管理方法／管理者を定めて管理する。テストベースは開発状況により改変される可能性があることを考慮する。
4.2.3
アーキテクチャスタイルに関する要求を獲得する

アーキテクチャスタイルを抽出するためにテスト要求を獲得する。アーキテクチャスタイルはテスト要求だけでなく、テストプロジェクトの習熟度などにも影響を受ける。

IVECにおけるアーキテクチャスタイルは以下の原則に従う：①テスト要求を実現するため必要な技術として普及しているもの、②テスト要求を実現できることを説明できること、③構造化されていること。

INPUT
  • テスト要求分析成果物
  • テストベース
  • アーキテクチャスタイル
  • 過去のテスト実績情報
OUTPUT
  • テストポリシー
  • 抽出したアーキテクチャスタイル
  • テストの種類の一覧
実施タスク
テスト要求分析の成果物からテストポリシーを定義する。各種アーキテクチャスタイルから適切なものを抽出し、包括されるテストの種類を一覧にする。前バージョンのテスト計画書から前回実施したテスト種類も一覧化する。
🎯 学習のポイント
テストアーキテクチャスタイルとは、テスト対象の品質が確保されることを表すための指標。ISO/IEC 25010を活用することもその一つ。例えばユーザ寄りのテストであれば利用時品質を用いてカバレッジを説明できる。
4.2.4
アーキテクチャスタイルの要求を分析する

抽出したアーキテクチャスタイルへの要求を分析する。基本的にテストレベルやテスト目的に合わせて選択するが、テストプロジェクトが得意とするスタイルや習熟度によるアプローチの変更も考慮する。

INPUT
  • テスト要求分析成果物・テストポリシー
  • テストベース
  • 抽出したアーキテクチャスタイル
  • 過去に実施したテスト種類の一覧
  • アーキテクチャスタイル要求分析の比較検討結果
OUTPUT
  • テストの種類一覧
  • テストアーキテクチャごとのメリット・デメリット
  • テスト手法の選択
  • テストサイクル・テストの優先度
  • 不具合発生率予想・不具合改修率
  • テスト対象機能の範囲内/外設定
  • プロダクトリスク一覧表
実施タスク
① テスト要求分析結果に沿うテスト種類をリストアップ
② テストアーキテクチャスタイルごとのリスク・コスト・メリットをリストアップ
③ 機能特性／非機能特性のテスト観点の理解
④ テスト対象の品質状態に合わせてテストエリアとテストの深度を定義
⑤ テスト対象の特性や開発状況を考慮してテストの優先順位を設定
⑥ 過去の実績・開発量・難易度などを考慮して不具合発生率を予測
⑦ テスト終了時の条件として不具合の改修条件を設定
⑧ プロダクトリスクを抽出
🎯 学習のポイント
プロダクトリスク抽出例：ISO/IEC 25010の品質特性モデルを利用する場合、機能性や性能効率性などを用いてシステムの水準を求める。担当するテストレベルの範囲外、特に次工程のテストレベルに影響するリスクは手戻り抑止のために意識する必要がある。
4.2.5
アーキテクチャスタイルを選択する

要求分析の結果に基づいてアーキテクチャスタイルを選択する。QCDMM分析を行って選択する。

INPUT
  • アーキテクチャスタイルの要求分析結果
  • プロダクトリスク一覧表
OUTPUT
  • アーキテクチャスタイル選択要素
  • テスト範囲・テスト手法・テストサイクル
  • テストスケジュール・QCD分析結果
実施タスク
QCDMM（Q：品質、C：コスト、D：納期、M：マネジメント、M：マーケット（ターゲット））の分析を行い、アーキテクチャスタイルを選択する。
4.2.6
テスト全体の構造を設計する

選択したアーキテクチャスタイルに基づいて各種テストを配置する。アーキテクチャスタイルによって実施されるテストの種類は一種類とは限らず、適切なテストをテスト要求に基づいて構成していく。

INPUT
  • アーキテクチャスタイル要求分析の選択結果
  • テストアーキテクチャスタイル別の分類要素
OUTPUT
  • スタイル別に分類した機能ブロック・ユースケース等の要素
  • テストアーキテクチャ毎の共通要素グループ・固有要素グループ
  • テストアーキテクチャグループ間のテスト関連表
実施タスク
① テストアーキテクチャスタイルに合わせてテスト対象のテストすべき要素（機能・ユースケース等）を配置
② テストアーキテクチャ別に共通項目・固有項目を分類
③ テストアーキテクチャ毎のグループ間のテストの関連性を検討・設計
4.2.7
テスト全体のバランスを調整する

選択されなかったアーキテクチャの影響を確認し、選択したアーキテクチャスタイルの実現可能性を検証する。テスト詳細設計の実施概要を検討する。

INPUT
  • テストベース
  • 適用可能なアーキテクチャスタイル素材
  • 過去に実施したテスト種類の一覧
  • テスト対象の特性要因
  • 非採用テストアーキテクチャの影響
  • テストアーキテクチャグループ間のテスト関連表
OUTPUT
  • テストアーキテクチャレビュー結果
  • テスト詳細設計概要
実施タスク
① 選択されなかったテストアーキテクチャを確認
② 選択したテストアーキテクチャスタイルの実現可能性を確認
③ 選択漏れ・矛盾がないことを検証・レビュー
④ テストアーキテクチャスタイルに基づきテスト詳細設計の実施概要を検討
🎯 学習のポイント
テスト詳細設計の実施概要検討で重要なのは設計のポリシーを明確にすること。「何を、どこまでテストするのか、それで何を担保するのか」を明示する。ポリシーが不明確だと大規模プロジェクトではテストタイプごとにテストする粒度が統一できなくなる。
4.2.8
テスト環境の構築方針・方法を検討する

テストベース・アーキテクチャスタイル・テスト手法等からテスト環境の構築方針を検討し、構築方法・必要なファシリティを確定する。

INPUT
  • テストベース
  • テストアーキテクチャグループ間のテスト関連表
  • テストアーキテクチャグループ別のテスト環境の構築方針
OUTPUT
  • テストアーキテクチャグループ別のテスト環境構築方針
  • テスト環境ファシリティ構成
実施タスク
① テストベース・アーキテクチャスタイル・テスト手法等からテスト環境の構築方針を検討
② テスト環境構築方針に基づき構築方法を検討
③ テスト環境構築方針・構築方法から必要とされるファシリティを検討
4.2.9
テスト詳細設計の指針・原則を検討する

品質目標とテスト技法を定義する。テスト対象物・テスト仕様書・テストデータの品質目標を数値で設定し、使用するテスト技法を選択する。

INPUT
  • テストベース
  • テスト要求分析による品質目標
  • テスト技法が記載されているドキュメント
OUTPUT
  • 品質目標の定義
  • テスト手法（技法）の定義
実施タスク
① テスト対象物の品質目標を設定する（テスト実施による不備指摘数）
② テスト仕様書・テストデータの品質目標を設定する（レビューによる不備指摘数）
③ テスト詳細設計で使用するテスト技法を選択する
4.2.10
テストアーキテクチャ設計成果物を作成する

4.2.5〜4.2.9の検討結果を整理してテスト計画書を作成する。テスト計画書は多岐にわたる要素を含む包括的な文書となる。

INPUT
  • 4.2.5〜4.2.9の成果物
OUTPUT（テスト計画書）
  • テストアーキテクチャ設計書
  • テスト範囲・テスト目的（目標値含む）
  • 終了基準・テストスケジュール
  • テストタスクWBS・テスト要員体制
  • リスク一覧表
  • 調達基準・技術要素トランスファー計画
  • プロジェクト改善計画（目標）
  • テスト環境定義
  • 品質目標・テスト手法（技法）定義
実施タスク
① 検討・設定した内容を用いてテスト計画書を作成する
② テスト環境関連をテスト計画書に記載する
③ 4.2.9で検討した内容を用いてテスト詳細設計の指針・原則をテスト計画書に記載する
4.2.11
テストアーキテクチャ設計成果物を検証する

テストアーキテクチャ設計成果物を要求元と公式レビューを行い、内容の過不足や整合性を確認する。4.1.5のテスト要求分析成果物の検証と同じ流れで実施する。

INPUT
  • テストアーキテクチャ設計成果物
OUTPUT
  • レビュー記録
  • レビューフォローアップ
  • 承認されたテストアーキテクチャ設計成果物
実施タスク
① 要求元・関係者と公式レビューを行い要求の漏れと整合性を確認
② 指摘事項があればレビュー記録に基づきフォローアップを行う
③ 全フォローアップ完了後、要求元の承認を得る

■ 四択問題
Q01四択4.2.2
テストベースを管理する際に定めるべき情報として適切でないものはどれか。
✅ 正解：D
テストベース管理で必要なのは履歴・管理場所・管理方法・管理者など。開発者の氏名はシラバスに規定されていない。また開発状況で改変される可能性を考慮することも重要。
Q02四択4.2.3
IVECにおけるアーキテクチャスタイルの原則として正しくないものはどれか。
✅ 正解：D
IVECのアーキテクチャスタイルはテスト要求だけでなくテストプロジェクトの習熟度などにより影響を受ける。同一スタイルを強制する原則は存在しない。
Q03四択4.2.4
アーキテクチャスタイルの要求分析の成果物として正しくないものはどれか。
✅ 正解：C
「承認されたテストアーキテクチャ設計成果物」は4.2.11（成果物の検証）のOUTPUT。4.2.4のOUTPUTはメリット・デメリット・プロダクトリスク一覧・不具合発生率予想などが含まれる。
Q04四択4.2.5
アーキテクチャスタイル選択時に行うQCDMM分析のMM（2つのM）が表すものはどれか。
✅ 正解：C
QCDMMはQ：品質(Quality)、C：コスト(Cost)、D：納期(Delivery)、M：マネジメント(Management)、M：マーケット（この場合はターゲット）。
Q05四択4.2.7
テスト全体のバランス調整において、設計のポリシーを明確にしないと大規模プロジェクトで起こる問題はどれか。
✅ 正解：B
ポリシー（何を、どこまでテストするのか）を明確にしないと、大規模プロジェクトではテストタイプごとにテストする粒度が異なり、統一した粒度でテストができなくなる。
Q06四択4.2.9
4.2.9「テスト詳細設計の指針・原則を検討する」で設定するテスト対象物の品質目標の指標として正しいものはどれか。
✅ 正解：A
テスト対象物の品質目標はテスト実施による不備指摘数。テスト仕様書・テストデータの品質目標はレビューによる不備指摘数。
Q07四択4.2.10
4.2.10でOUTPUTとして作成されるテスト計画書に含まれる要素として、シラバスに記載されていないものはどれか。
✅ 正解：D
テスト計画書に含まれる要素は「テストアーキテクチャ設計書・テスト範囲の定義・自動化・再利用化の定義・テスト目的・終了基準・テストスケジュール・テストタスクWBS・テスト要員体制・リスク一覧表・調達基準と技術要素トランスファー計画・プロジェクト改善計画・テスト環境定義・品質目標・テスト手法定義」。担当者の資格一覧は含まれない。
Q08四択4.2.4
アーキテクチャスタイルの要求分析において、担当するテストレベルの範囲外、特に次工程に影響するリスクに注目する主な理由はどれか。
✅ 正解：B
次工程のテストレベルに影響するリスクは手戻りを抑止するために意識する必要がある。担当するテストレベルでは、抽出したリスクを考慮してテストアーキテクチャ設計を進める。

■ 記述問題
Q14記述4.2.4
アーキテクチャスタイルの要求分析においてプロダクトリスクを抽出する際、担当するテストレベルの「範囲外」のリスクにも注目する理由を説明せよ。
📝 解答例
担当するテストレベルの範囲外、特に次工程のテストレベルに影響するリスクは手戻りを抑止するために意識する必要があるため。担当するテストレベルで抽出したリスクを考慮してテストアーキテクチャ設計を進めることで、後工程での手戻りを防ぐことができる。
Q15記述4.2.5
QCDMM分析の5つの要素を全て挙げ、それぞれが意味するものを説明せよ。
📝 解答例
Q：品質（テスト対象の品質水準）、C：コスト（テスト活動にかかる費用）、D：納期（テスト完了のスケジュール）、M：マネジメント（テストプロジェクトの管理）、M：マーケット（テストのターゲット・対象市場）の5要素。これらを総合的に分析してアーキテクチャスタイルを選択する。
Q16記述4.2.7
テスト詳細設計の実施概要を検討する際に「設計のポリシー」を明確にすることが重要な理由を、大規模プロジェクトを例に挙げて説明せよ。
📝 解答例
設計のポリシーとは「テストの目的や、何を、どこまでテストするのか、それでなにを担保するのか」を明確に示した方針。ポリシーを明確にしないと、大規模プロジェクトではテストタイプごとにテストする粒度が異なり、統一した粒度でテストができなくなるため。
Q17記述4.2.8
4.2.8「テスト環境の構築方針・方法を検討する」の3つの実施タスクを順番に説明せよ。
📝 解答例
①テストベース・アーキテクチャスタイル・テスト手法等からテスト環境の構築方針を検討する。②テスト環境構築方針に基づき、テスト環境の構築方法を検討する。③テスト環境構築方針と構築方法から、必要とされるファシリティを検討する。
Q18記述4.2.3
アーキテクチャスタイルに関する要求を獲得する際に、前バージョンのテスト計画書を参照する目的を説明せよ。
📝 解答例
前バージョンで実施したテスト種類を一覧化するため。過去の実績情報としてアーキテクチャスタイルの検討材料（INPUT）として活用する。

Qアーキテクチャスタイルの選択に影響を与える2つの要素は？
①テスト要求　②テストプロジェクトの習熟度など
Qアーキテクチャスタイルの要求分析で行う5つの分析内容は？（実施タスクより）
①機能特性／非機能特性のテスト観点の理解　②テスト対象の品質状態に合わせてテストエリア・テストの深度を定義　③テスト対象の特性・開発状況を考慮してテストの優先順位を設定　④過去の実績・開発量・難易度などを考慮して不具合発生率を予測　⑤テスト終了時の条件として不具合の改修条件を設定
Q次工程のテストレベルに影響するリスクに注目する理由は？
手戻りを抑止するため。担当するテストレベルで抽出したリスクを考慮してテストアーキテクチャ設計を進めることが求められる。
QQCDMM分析の5要素を全て答えよ。
Q：品質(Quality)　C：コスト(Cost)　D：納期(Delivery)　M：マネジメント(Management)　M：マーケット（ターゲット）
Qテスト全体の構造設計で分類する2種類の項目は？
共通項目と固有項目。テストアーキテクチャ別にこれらを分類し、グループ間のテストの関連性を検討・設計する。
Qテスト詳細設計の「設計のポリシー」とは？
テストの目的や「何を、どこまでテストするのか、それでなにを担保するのか」を明確に示した方針。
Q4.2.7のOUTPUT2つは？
①テストアーキテクチャレビュー結果　②テスト詳細設計概要
Qテスト環境の構築方針検討で考慮する主なINPUT3つは？
①テストベース　②テストアーキテクチャグループ間のテスト関連表　③テストアーキテクチャグループ別のテスト環境の構築方針
Q4.2.9で設定する品質目標2種類とその指標は？
①テスト対象物の品質目標：テスト実施による不備指摘数　②テスト仕様書・テストデータの品質目標：レビューによる不備指摘数
Q4.2.10の作成成果物（テスト計画書）に含まれる主な要素を6つ以上挙げよ。
テストアーキテクチャ設計書、テスト範囲の定義、終了基準、テストスケジュール、テストタスクWBS、テスト要員体制、リスク一覧表、調達基準と技術要素トランスファー計画、プロジェクト改善計画（目標）、テスト環境定義、品質目標の定義、テスト手法（技法）の定義
Q4.2.11「テストアーキテクチャ設計成果物を検証する」の3ステップは？
①要求元・関係者と公式レビューを行い要求の漏れと整合性を確認　②指摘事項があればレビュー記録に基づきフォローアップ　③全フォローアップ完了後に要求元の承認を得る
Q4.2.3で「テストポリシー」を定義するINPUTは何か？
テスト要求分析の成果物から定義する。
Qアーキテクチャスタイルごとのメリット・デメリットと合わせてリストアップすべき項目は？
リスク・コスト・メリット等（アーキテクチャスタイルごとにリスク・コスト・メリット等をリストアップする）
Qテストベースの管理で「テストベースが改変される可能性がある」とはどういう意味か？
テストベースは開発中に仕様変更等により更新される可能性があるため、バージョン管理を含めた管理体制が必要であることを指す。
Qテスト全体の構造設計の3つのOUTPUTは？
①テストアーキテクチャスタイル別に分類した機能ブロック・ユースケース等の要素　②テストアーキテクチャ毎の共通要素グループ・固有要素グループ　③テストアーキテクチャグループ間のテスト関連表
Q4.2.8のOUTPUT2つは？
①テストアーキテクチャグループ別のテスト環境の構築方針　②テスト環境ファシリティ構成
Q4.2.9のOUTPUT2つは？
①品質目標の定義　②テスト手法（技法）の定義
Q4.2.5のINPUT2つは？
①アーキテクチャスタイルの要求分析結果　②プロダクトリスク一覧表
